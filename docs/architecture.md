# Architecture

## Planned system

ServiceDesk AI is an AI receptionist for a fictional auto repair shop. The full
system has these components:

### Voice AI + Conversation Workflows (planned, not implemented)
Telnyx Voice AI and native Conversation Workflows handle inbound calls. The
receptionist greets callers, understands intent, and routes to the MCP server
for service catalog lookup, availability checks, and booking creation.

### MCP server (planned, not implemented)
A Model Context Protocol server exposing three tools:
- `get_service_catalog` — returns available auto repair services
- `get_availability` — returns open appointment slots for a given date range
- `create_booking` — creates an appointment (idempotent)

The official `examples/ts/mcp-server/` in the edge-compute repo demonstrates an
MCP server over streamable HTTP on Edge Compute. That example uses `func.toml`;
our MCP server will live inside the `telnyx.toml` project alongside the actors.

### Telnyx KV (planned, not implemented)
Holds the service catalog and configuration. Accessed via a
`[storage.kv.<name>]` binding declared in `telnyx.toml`. Note: `[storage.kv]`
bindings are **not available in local `dev`** (only in deployed functions).

### Stateful Actor — per shop/day (planned, not implemented)
One actor instance per shop per day owns that day's appointment state. It
coordinates booking operations and provides idempotent retries. The actor uses
`ctx.storage` (key-value) and/or `ctx.storage.sql` (per-instance SQLite) for
durable state. Single-threaded dispatch guarantees safe read-modify-write
without locks. Named by convention, e.g. `shop-<id>-<date>`.

### Dashboard (planned, not implemented)
A small dashboard showing operational metrics and a booking funnel based on
real events. Built from function logs, invocation metrics, and actor state.

### Follow-up agent (future expansion, explicitly out of scope)
Not part of current work.

### What is verified vs. what is not

**Verified (mocked unit tests):** routing logic, health response shape (public,
no secrets), HTTP method handling, request body parsing, 404 behavior, and the
full auth gate: absent/empty/rejecting secret binding → 503; missing/malformed/
incorrect bearer credential → 401; valid credential → Actor reached; Actor
never called on any rejected request (6 scenarios, 13 tests). TypeScript strict
compilation (0 errors).

**Verified (local runtime — `telnyx-edge dev`, before auth gate):** real actor
persistence via `ctx.storage.get/put` against the live local backend; per-name
instance isolation; cumulative state across requests; persistence across full
stack stop/restart (volumes preserved); 20 concurrent increments (bounded to 5)
with zero lost updates. See `docs/verification.md` for details.

> **Note:** Subtasks 1.2 and 1.3 ran before the auth gate (1.4) was added. Local
> `dev` does not emulate `[[secrets]]`, so demo routes now return `503` locally.
> Those earlier results remain valid for what they tested (persistence,
> concurrency) but cannot be reproduced as-is without removing the auth gate.

**NOT verified:** remote deployment behavior (`ship`/`func_id`); `[storage.kv]`/
`[telnyx]` bindings (unavailable in local `dev`); actor rehydration after
volume-destroying restart; concurrent dispatch at production scale.

### Template provenance

The project files were transcribed from official documentation (README, Quick
Start, Project Structure) because `telnyx-edge new-func --actor` requires
authentication and registers a function resource before writing template files
(provisioning, which was out of scope). The transcribed shapes match the
documented contract, but may not match v0.5.12's default scaffold byte-for-byte.
